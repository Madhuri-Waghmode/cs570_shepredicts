## Part 1. Target and History Features

### Target
`add_label` in `src/data.py` sets `label = 1` when `Rating >= 4` and `label = 0` otherwise. It is added after the repairs
and joins and before the split. 57.89% of training rows have `label = 1`.

### Decide 1: Ratings Used by Each History Feature

| Feature | Training row with timestamp $t$ | Test / scoring row |
| :--- | :--- | :--- |
| **`user_count`** | Number of training ratings by the same `UserID` with `Timestamp < t` (that is, `<= t - 1`). The current row, ratings in the same second, and later ratings are excluded. | Number of all training ratings by the same `UserID` (`Timestamp < 2000-12-01 00:00:00 UTC`). No test rating is used. 0 if the user has no training rating. |
| **`user_avg`** | Mean `Rating` of the same ratings as `user_count`. `null` when `user_count = 0`, before the fallback fill. | Mean `Rating` of all training ratings by the same `UserID`. `null` when the user has no training rating, before the fallback fill. |
| **`movie_count`** | Number of training ratings of the same `MovieID` with `Timestamp < t`. The current row, ratings in the same second, and later ratings are excluded. | Number of all training ratings of the same `MovieID`. No test rating is used. 0 if the movie has no training rating. |
| **`movie_avg`** | Mean `Rating` of the same ratings as `movie_count`. `null` when `movie_count = 0`, before the fallback fill. | Mean `Rating` of all training ratings of the same `MovieID`. `null` when the movie has no training rating, before the fallback fill. |

Training rows use a Spark window per `UserID` (or `MovieID`), ordered by `Timestamp`, with
`rangeBetween(Window.unboundedPreceding, -1)`. Timestamps are whole seconds, so the frame ends one second before the
current row. Test rows get the per-user and per-movie totals of the training rows through left joins, so every test row
is kept. Missing counts are set to 0, and missing averages stay `null` until `fill_history` replaces them.

### Decide 2: Why Test Rows Use Only Training Ratings, Even When Earlier Test Ratings Exist
The test rows stand for ratings we must predict without knowing them, as in D3 scoring of held-back rows and in
production. If a December test row used earlier December ratings, two things would go wrong:
1. **Leakage**: the features would depend on test outcomes (`Rating`, `label`) that are not available at prediction time.
2. **Inconsistent evaluation**: a row's prediction would depend on which other test rows happen to be present and in
   what order, so the test score would not reflect how the model behaves on new rows.

Fixing the history of every test row to the training period makes the test features independent of test outcomes.
The same code then works on production rows that have no `Rating` column at all.

### Decide 3: Checking the History Rule and Row Preservation
`python src/check_history.py` wrote `reports/history_check.csv`:

```csv
check,changed_row,passed
strictly earlier history,b,True
scoring history independent of outcomes,all scoring rows,True
```

1. **Strictly earlier history**: the harness changes row `b` (Timestamp 200) from rating 4 to 1 and rebuilds the history.
   The earlier rows (Timestamp 100), the same-second rows `same_user` and `same_movie` (Timestamp 200), and `b` itself
   keep their features. `later_user` and `later_movie` (Timestamp 300) change, from an average of 3.0 to 2.0. So the
   window uses only strictly earlier ratings. The exact expected histories also match, before and after the change.
   If ratings in the same second were included, `same_user` and `same_movie` would see `b`'s new rating, their
   features would change, and the check would fail.
2. **Scoring independent of outcomes**: the scoring rows get the same training-only counts and averages whether their
   ratings are the originals, reversed (6 − Rating), or removed. Users and movies not seen in training get count 0 and
   average `null`.
3. **Row preservation on the real data**: `add_history` returns 791,270 training rows and 113,487 test rows, the same
   counts as its inputs. The test set has 669 users with no training ratings (85,086 test rows, 75% of the test set)
   and 16 movies with no training ratings (17 test rows). These rows depend on the fallback value in Part 2.
   `python src/build_dataset.py` printed `Training rows 791,270, test rows 113,487` and `Check, rows unchanged: True`:
   every row from the split survives the full feature build, encoding, and vector assembly, so no row is lost.

## Part 2. Feature Completion and Dataset Checks

### Decide 1: Training-Only Fallback for Missing History Averages
`fallback_value` calculates the mean `Rating` from the 791,270 training rows only. The build's fallback was **3.5912**
stars. `fill_history` uses it for a missing `user_avg` or `movie_avg`; test ratings are not used to calculate it.
Missing history counts are set to zero before the flags are created.

### Decide 2: Rows with No Earlier User or Movie History
`user_new = 1` identifies a row whose `user_count` is zero; `movie_new = 1` identifies a row whose `movie_count` is
zero. The flags are calculated separately, so a row can have either or both flags set. Percentages use the complete
split DataFrame: flagged rows divided by total rows in that split, multiplied by 100.

| Split | Total rows | Rows with `user_new = 1` | Percentage | Rows with `movie_new = 1` | Percentage |
| :--- | ---: | ---: | ---: | ---: | ---: |
| Training | 791,270 | 13,274 | 1.678% | 3,662 | 0.463% |
| Test | 113,487 | 85,086 | 74.974% | 17 | 0.015% |

### Decide 3: Validation Results and Difference from the D1 Part 6 Plan
The dataset build passed both checks: **row counts unchanged** (`True`) and **no nulls in the vector inputs** (`True`).
The sample report also includes a `user_new = 1` row with `user_count = 0` and `user_avg = 3.5912`, the training
fallback. The history checks passed for strictly earlier training history, row preservation, and scoring histories
independent of scoring outcomes.

D1 Part 6 proposed log-transformed, standardized prior counts; smoothed user/movie positive-label rates; a global
positive-rate fallback; and static `release_year`, `genre_count`, and zip-region features. The implemented model
instead uses `log1p` history counts without standard scaling, average star `Rating` as the user/movie history value,
and the training mean rating (3.5912) as the missing-average fallback. It includes gender, the training genre
indicators, and one-hot age and occupation, but does not include `release_year`, `genre_count`, or zip region.
The history features still use strictly earlier training ratings for training rows and training-only history for test
rows, as planned.

## Part 3. Baselines and Evaluation

### Decide 1: Baseline Selection


We evaluated two simple baseline methods to predict whether a user would give a movie a positive rating.

The majority baseline always predicts the most common class in the training data. In our dataset, the majority class is label 1 (positive rating), representing 57.89% of training rows. This baseline does not use any historical features.

The rule-based baseline uses the movie_avg feature to predict whether a rating will be positive. The choose_rule_threshold() function compares candidate thresholds using training data and selects the threshold with the highest training accuracy. If two thresholds have the same accuracy, the lower threshold is selected.

Selected threshold: 3.5

Rule-based baseline training accuracy: 0.6790 (67.90%).

Baseline test accuracy results: The majority baseline achieved 57.54% accuracy, while the rule-based baseline achieved 68.40% accuracy.


### Decide 2: Evaluation and Accuracy Breakdown

We evaluate the baseline predictions using the test dataset.

The accuracy_breakdown() function calculates prediction accuracy for different groups:

Overall: All test rows.

Both histories (warm rows): Rows where both the user and movie have historical information.

Fallback (cold-start rows): Rows requiring fallback values because historical information is missing.

| Evaluation Group | Number of Rows | Majority Accuracy | Rule Accuracy |
|---|---:|---:|---:|
| Overall | 113,487 | 57.54% | 68.40% |
| Both histories (warm rows) | 28,397 | 53.77% | 67.82% |
| Fallback (cold-start rows) | 85,090 | 58.80% | 68.59% |

The accuracy breakdown helps us understand how the baseline performs when historical information is available and when fallback values are needed.

Observation: The rule-based baseline performed better than the majority baseline in all three groups. Overall, it achieved 68.40% accuracy compared with 57.54% for the majority baseline. The fallback group had slightly higher rule accuracy than the warm group.

For both baselines, the warm group had lower accuracy than the fallback group. The majority baseline achieved 53.77% accuracy on warm rows compared with 58.80% on fallback rows. Similarly, the rule-based baseline achieved 67.82% on warm rows compared with 68.59% on fallback rows.
